# 第1回 解答

## 演習

- 講座に固有の質問（宿題の3レベル）へのモデルの回答（要約でよい）：
  gemini-3.5-flash-lite は「講座によって定義は異なるが、一般的には初級・中級・上級（基礎・応用・発展）の3段階の難易度のこと」と答え、各レベルの内容を一般論で並べたうえで「LMS や Slack で確認してください」と締めた。講座のことを知らないとは言わず、一般論でもっともらしく答えた。
- 用語集の正しい意味と比べて気づいたこと：
  用語集では「基礎（講義内容の確認）・実装（自分でコードを書く）・発展（調査や試行）」の3段階で、どれか1つに取り組めば完了、原則として採点しない、となっている。モデルの答えは「段階が3つある」点だけ合っていて、名前は「基礎・応用・発展」のように一部だけ偶然近かった。「どれか1つで完了」「採点しない」という一番大事な点は、宿題の計測で集めた11回の回答のどれにも出てこなかった。gemini-3.8-flash は「レベル1が必須・合格ライン」と、確信を持って違うことを書いていた。
- 表示できたトークン数（入力 / 出力）：
  `app/ask.py` で `response.usage_metadata` の `prompt_token_count` と `candidates_token_count` を表示するようにした（思考トークンがあれば別に表示）。
  - 「LoRAとは何ですか？」：入力 7 / 出力 568
  - 「3レベル」の質問：入力 21 / 出力 553

### やったこと

- 基礎：「3レベル」の質問を、モデルと temperature を変えて3回ずつ実行した（`scripts/measure_lec01.py --plan basic`）。temperature は `generate_content` の `config=GenerateContentConfig(temperature=...)` で渡した。
- 実装：`app/ask.py` に `Conversation` クラスと `--chat` オプションを足し、会話履歴を保ったまま続けて質問できるようにした。API は状態を持たないので、毎回それまでのやりとりを全部 `contents` に入れて送る。`/reset` で履歴を消せる。API を呼ばないテスト `tests/test_ask.py` を追加し、`uv run pytest -q` は14件すべて通る。
- 発展：応答時間とトークン数を測るスクリプト `scripts/measure_lec01.py` を書いた。3つのモデルと3つの質問（長く答える「LoRA」、講座固有の「3レベル」、一言で終わる「日本の首都」）で測り、全結果を `lectures/01/results/measurements.csv` に、回答本文を `answers.jsonl` に保存した。途中からストリーミングでも呼び、最初の文字が届くまでの時間（TTFT）も測った。レート制限を超えないよう呼び出しの間を flash-lite は5秒、3.8-flash は15秒あけ、エラーも1行として記録した。

### 気づき・疑問

- 応答時間は出力の長さではあまり決まらなかった。3.5-flash-lite は「日本の首都」の出力が2〜3トークンなのに平均20秒かかり、650トークン前後の LoRA の説明（13秒）より遅かった。ストリーミングで測ると、3.5-flash-lite の LoRA は全体33秒のうち30秒が最初の文字が届くまでの待ちで、文章の生成そのものは3秒ほどだった。待ち時間の大半は、混雑によるサーバー側の順番待ちだと考えている。
- 同じモデルでも時間帯で大きくぶれた。前半の通常呼び出しでは3.5-flash-lite は10〜20秒だったが、10分ほど後のストリーミングでは26〜72秒になった。3.1-flash-lite は答えが返れば4秒前後と速い一方、10回に1回以上の割合で 503 が返った。1回ずつの数字は信用しきれないので、平均と最小・最大を並べ、失敗した回も消さずに残した。
- gemini-3.8-flash は出力とは別に思考トークンが 995〜1250 あり、出力の1.3〜1.9倍だった。表示される答えの長さは lite と同じくらいでも、裏で使うトークンと時間は多い。一言で答える質問では思考は42トークンだけで、速さも lite と変わらなかった。
- レート制限との関係：毎分の上限（lite は15）は、1回に10〜40秒かかる今回のような順番の呼び出しではほとんど効かず、1分に2〜6回しか呼べていない。効いてくるのは1日の上限のほうで、今回の計測だけで3.5-flash-lite に21回、3.1-flash-lite に15回使った（演習と会話モードの確認を入れるとさらに6回）。gemini-3.8-flash は1日10〜20回前後なので、5回試すだけで1日分の2.5〜5割を使い、そのうち2回は 503 で答えが得られなかった。強いモデルは「数問だけ確かめる」用途に絞るのがよいと実感した。第3回以降のエージェントは1つの質問で何回も LLM を呼ぶので、仮に1問5回なら lite でも1日100問ほどで上限に届く。
- 503 はレート制限（429）ではなく、モデル側の混雑による失敗で、自分の使い方を減らしても避けられない。混んでいるときは別のモデル（3.1-flash-lite など）に切り替えるか、少し待ってやり直す仕組みが要りそうだと思った。今回は、通信が切れたまま約4分応答がなく、計測が止まったことが1回あった。そのあとスクリプトに90秒のタイムアウトを入れ、途中で止まっても続きから測れるようにした。
- temperature 0 でも答えが毎回変わった理由は分かっていない。サーバー側の並列処理による非決定性なのか、Gemini 3 系では temperature の効き方が変わったのかは、第2回の「生成設定と出力の揺れ」で確かめたい。

### AI ツールの使い方と、自分で確かめたこと

コードと answer.md の下書きには AI のコーディング支援を使った。そのうえで、次のことは自分で実行や目視で確かめた。

- `uv run pytest -q` が通ること（既存の11件と追加の3件）
- `--chat` で2ターン目に前の答えを踏まえた返事が来ること、`/reset` で履歴が消えること、入力トークンが増えること
- 表の数字が `measurements.csv` と合っていること、503 や通信エラーの回も表に入っていること
- 「3レベル」の回答11件を読んで、「どれか1つで完了」「採点しない」に触れたものがないこと
- API キーがコード、ログ、CSV、answer.md、コミットのどこにも入っていないこと（`git grep` で確認）
