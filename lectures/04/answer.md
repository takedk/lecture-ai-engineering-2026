## 宿題

- 取り組んだレベル：発展
- やったこと：
  - フロンティアモデルの評価で使われる [SWE-bench Verified](https://www.swebench.com/verified) を選んだ。公式の説明は OpenAI のブログ [Introducing SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)（2024-08-13）と、注釈手順書、Hugging Face の Dataset Viewer（[SWE-bench/SWE-bench_Verified](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified)）を読んだ。
  - 問題を 5 件読んだ（全文は貼らず、要約だけ書く）。
    - `astropy__astropy-12907`（15分〜1時間）：入れ子の CompoundModel で `separability_matrix` が、同じ構造をネストすると独立であるべき入出力を非独立と判定する。行列の見た目を追えば再現はできるが、ライブラリ内部の結合の扱いに詳しくないと直しきれないと思った。
    - `astropy__astropy-13033`（15分〜1時間）：TimeSeries から必須列を消したときの例外文が、必須列は `time` だけという前提のままなので分かりにくい。メッセージを直せばよく、自分でも解けそうだが、必須列の定義箇所をコードで確認する必要はある。
    - `django__django-15572`（15分未満）：`TEMPLATES["DIRS"]` に空文字が入ると、pathlib 正規化のあとで空文字がプロジェクトルート扱いになり、テンプレート変更と誤認してオートリロードが止まる。原因と直し方が issue にかなり具体的で、LLM でも条件を見落とさなければ解けそうに見えた。
    - `django__django-15629`（1〜4時間）：主キーに付けた `db_collation` が外部キー側に伝わらず、MySQL で制約エラーになる。マイグレーション SQL の順と照合順の伝播を追う必要があり、フレームワークの内部に詳しくないと難しい。
    - `astropy__astropy-13398`（1〜4時間）：ITRS から観測座標への変換を、地球中心の光行差を経由せず ITRS 内で扱う提案。天文学の座標系の知識が要り、自分ではすぐには解けない。テストも屈折や天頂方向など複数ある。
  - 作成と検証の手順（ブログと注釈手順より）：元データは GitHub の解決済み issue と、対応する PR のテスト。OpenAI が Python 経験のある開発者 93 人を集め、SWE-bench テスト集合から無作為に選んだ 1699 件を注釈した。各件を独立に 3 人が見る。見る観点は、issue 文が不十分で不公平になっていないか、`FAIL_TO_PASS` テストが正しい解まで落としていないか（重大度 0〜3。2 と 3 は除外）。開発者の所要時間の見積もりも取り、easy（15分未満）196 件、hard（1時間超）45 件といった切り出しができる。ここから問題の少ない 500 件を SWE-bench Verified とした。採点は、モデルにはテストを見せず、提出したパッチのあとで `FAIL_TO_PASS` と `PASS_TO_PASS` を走らせ、両方通れば正解、というテスト採点である。
- 結果：
  - 今日の評価セット（10 件、講師 1 人が作成、人と LLM で採点、決められないものは unsure）との違い：規模（10 対 500）、作成に関わった人数（講師 1 人対 93 人＋3 名独立の検証）、採点方法（ルーブリックに照らした人／LLM の T/F 対、隠したユニットテスト）、除外の手続き（今日は仕込んだ失敗を残して観察する。Verified は不十分な問題を落としてから使う）が大きく違う。今日いちばん大事だった「基準に書いていないことをどうするか」は、SWE-bench では注釈の段階で問題ごと除外するか、テストの範囲を見直すことに相当する。逆に、形式のチェックをコードで行う点は、今日の「回の表示」と方向は近い。
- 気づき・疑問：
  - 同じ「評価セット」でも、誰が何人で検証し、何を除外し、どう採点するかで、数字の意味がまったく変わる。モデルのスコアだけを見ても、その裏の作り方を見ないと過大評価や過小評価になりそうだと感じた。
  - 問題文が丁寧でも、テストが何を見ているかは文面だけでは分からない。LLM が issue の言い回しだけに合わせて、テストが想定する周辺ケースを外すこともあり得る。今日の「人と LLM の一致率を見てから採点器を信じる」という順番は、こうしたベンチマークを読むときにも必要だと思った。
  - 演習の LLM 本採点は API キーがなく実行できなかった。発展の調査自体はコード不要で完了している。
